# AGENTS.md

Native Android app (Kotlin + Compose) that runs an **OpenCode v2 server inside proot + Alpine** and drives it over its HTTP/SSE API. No JNI bridge, no terminal scraping, no protocol translation.

Authoritative plan: `docs/specs/OpenCode Mobile – Build Spec.md`. Read it before implementing anything — it defines the runtime layout, the exact API surface, and the phase plan. Items marked `[VERIFY]` are unresolved; **resolve them by testing, never by guessing.**

## Build

```sh
ANDROID_HOME=~/Android/Sdk sh gradlew :app:assembleDebug   # verified working
ANDROID_HOME=~/Android/Sdk sh gradlew :app:testDebugUnitTest --rerun-tasks
```

Two environment quirks, both of which break the build silently otherwise:

- `gradlew` is **not executable** (`-rw-r--r--`). Always `sh gradlew …`, never `./gradlew …`.
- There is **no `local.properties` and no `ANDROID_HOME`** in the environment. Without the prefix, `assembleDebug` fails at configuration with *"SDK location not found"*. Either prefix every command or write `sdk.dir=/home/musa/Android/Sdk` into `local.properties` (gitignored).

Java 17 only (`JAVA_HOME` points at a Temurin 17 in `~/.local/share/jdks`). Gradle 9.0.0, AGP 8.13.0, Kotlin 2.1.0. First build is slow (~2m40s cold); the daemon is long-lived (`idletimeout=10800000`).

`--rerun-tasks` is **required** on the test task. Without it the task reports UP-TO-DATE and a broken test looks green.

No lint, detekt, ktlint, or CI config exists. Don't invent commands or assume a check runs on commit.

## Verification that actually matters here

`assembleDebug` passing proves almost nothing — the runtime only exists on a device. For anything server-facing, install and run:

```sh
ANDROID_HOME=~/Android/Sdk sh gradlew :app:installDebug
adb shell monkey -p com.musa.opencodeharness -c android.intent.category.LAUNCHER 1
adb shell screencap -p /sdcard/s.png && adb pull /sdcard/s.png
```

`adb reverse tcp:<port> tcp:<port>` lets the device reach a server on the dev host — that is how the client's behaviour was verified against a live OpenCode server.

## Android specifics

- SDK levels are **inconsistent on purpose for now**: `compileSdk 36`, `targetSdk 34`, `minSdk 30`. The spec's sideload-vs-Play reasoning (§8) depends on these; change them deliberately, not as drive-by edits.
- The application id is `com.musa.opencodeharness` (namespace + applicationId), but the spec says `org.musa.<appname>` with the name TBD. **This is unresolved** — don't rename without asking, and keep new packages consistent with whatever id currently exists.
- `AndroidManifest.xml` declares `FOREGROUND_SERVICE_DATA_SYNC`. The spec leaves the foreground-service type as `[VERIFY]`, so treat the current manifest as provisional.
- Target is **arm64-v8a only** — the proot binary ships as `jniLibs/arm64-v8a/libproot.so` (not present yet). Don't add other ABIs.
- Kotlin 2.1.0 caps the dependency versions: kotlinx-serialization 1.8.1 / Ktor 3.2.4 are the newest that compile. Newer ones need Kotlin 2.2+, and Ktor 3.6.0 additionally needs compileSdk 37. Don't "upgrade" them casually.

### Two permissions that are not optional

- **`INTERNET`** — without it Android denies every socket, including loopback. Found by a device spike, not by reading docs.
- **Cleartext to loopback** — `targetSdk 34` denies cleartext by default, so requests to the in-proot server fail with `CLEARTEXT communication to 127.0.0.1 not permitted`. Fixed with `res/xml/network_security_config.xml` scoped to `127.0.0.1`/`localhost`/`::1` — **not** `usesCleartextTraffic="true"`, which would permit cleartext to every host including providers.

## Conventions

- **Kotlin DSL only** — all Gradle files are `.kts`. Match it in anything new.
- Dependencies and plugin versions are declared as `libs.*` aliases in `gradle/libs.versions.toml`. Add entries there, don't inline a coordinate in `app/build.gradle.kts`.
- Several files carry `// Plugins automatically generated by TLGradle.kt` / `MLGradleWriter.kt` markers — these came from AndroidIDE. Hand edits survive, but expect AndroidIDE regeneration to be able to overwrite them; keep changes minimal and deliberate.
- 25 JVM unit tests exist. Fixtures are the real captures in `docs/samples/`, wired onto the test classpath as resources via a `sourceSets` `resources.srcDir` — don't copy them into the source tree.
- Package layout: `data/` (client + models + `SessionTree.kt`), `ui/` (theme), plus the screen layer. Follow the spec's section numbers when adding more.

## Runtime: proot on device

All verified on a real OPPO Reno 3 (PCLM50), Android 12 / SDK 31, arm64-v8a. `docs/phase0-findings.md` is the full record. Every item below was found by hitting the failure:

- **`PROOT_LOADER` must be set.** The Termux proot build hardcodes a Termux loader path; from the app sandbox it fails with `the loader was not found or doesn't work`. Ship our own `loader` binary.
- **`LD_LIBRARY_PATH` must include the proot lib dir.** It needs `libtalloc.so.2` and `libandroid-shmem.so`, or it fails to link.
- **musl binaries cannot exec from `/data/local/tmp`** (rc=126). The runtime must live in `filesDir`.
- **Set `PATH=/bin:/sbin:/usr/bin:/usr/sbin`, `HOME=/root` and `TMPDIR` explicitly**, or the guest inherits Android's environment and `cat`/`ls`/`apk` all report "not found".
- **Clear `lib/apk/db/lock` on resume.** An interrupted `apk` run leaves a lock and every later run fails with `Unable to lock database`. This is the concrete failure behind the spec's "resumable after process death" requirement.
- **Network diagnostics must run in the app's own process, never via `adb shell run-as`.** `run-as` sits in a different SELinux domain without the `inet` group, so every socket reports `Operation not permitted` while the app itself has full network. This is what spec §3.5's Diagnostics screen has to get right.

Working invocation: `proot -0 --link2symlink -r <rootfs>` with the env above; `-b` binds were not needed.

## Runtime invariants worth not breaking

- The OpenCode server binds **loopback only** and requires HTTP Basic auth (user `opencode`, password from `OPENCODE_SERVER_PASSWORD`). The app must always set that variable; unset means the server runs unsecured with only a printed warning.
- proot shares Android's network namespace, so the app reaches the in-proot server on `127.0.0.1` — no extra plumbing.
- OpenCode's config and data dirs are bind-mounted from app storage **outside** the rootfs, so rootfs reinstalls must never wipe sessions or credentials. Preserve that when touching the proot launch flags (§2.2).
- Provider keys live in OpenCode's own data dir inside app-private storage, not in the app's Keystore. Never log them; redact in diagnostics output.

## API facts that differ from the spec

`docs/phase0-findings.md` has the evidence. The traps:

- **Health is `GET /api/health`**, not `/api/info` — `/api/info` does not exist and returns the SPA's HTML, so a naive probe "succeeds" with `text/html`.
- **Envelopes differ per endpoint.** `/api/session` returns `{data, cursor}` with **no** `location`; `/api/agent`, `/api/command`, `/api/model`, `/api/fs/list` return `{location, data}`. Both keys are optional in `Envelope` so either decodes.
- **Agents have no `name` field** (0 of 32 on the real capture) — `displayName` falls back to `id`. `mode` is `primary` / `subagent`.
- **A session's own `location` has only `directory`**, while the envelope-level `location` has `{directory, project}`. One `Location` type decodes both.
- **There is no children-listing route.** Sub-agent sessions are just `SessionInfo.parentID`; the tree is built client-side by `buildSessionTree`.
- **A session is a sub-agent iff `parentID != null`** — not iff it has no children. A promoted orphan has a parent *and* no children, so the children-based rule is wrong on real data (holds for 47/50).
- **Attachments use `uri`, not `path`** (`PromptInput.FileAttachment`); an inline-base64 variant also exists.
- **`/api/event` is SSE, not a WebSocket.** `ktor-client-websockets` is for the PTY endpoint (spec §5.5). SSE already arrives transitively through it as `io.ktor:ktor-sse`, which carries the `sse { }` client plugin. There is **no `ktor-client-sse` coordinate** — adding one fails to resolve, so the streaming task needs no new dependency.
